# HGhub 播放流畅度分析

## 结论

优先修正下载取消、前台优先级与预取隔离，再补齐移动端拖动和跨视频预热。现有 60 秒 HLS 缓冲、分片 singleflight、内存/磁盘缓存及 8 路 Range 下载已经存在，继续单纯放大缓冲或并发不是首选。

本轮只分析、运行离线测试、增加此文档；未修改业务代码、配置或重启用户实例。仓库开始时已有多处未提交改动，保持原样。

证据等级：**现场实测**指本轮运行结果；**源码确认**指代码路径/缺陷成立，但其现场发生频率未量化；**历史参考**指已有调优记录，未当作本轮 CDN 实测。

## 优先处理的问题

### P0：取消下载后前台计数泄漏，Range 子任务继续占带宽

**源码确认。** [前台下载](../src-tauri/src/media.rs#L703-L710) 在 await 前加 `FOREGROUND_ACTIVE`、await 后减；[推测预取](../src-tauri/src/media.rs#L1091-L1130) 会 abort 正在执行 `load_segment()` 的任务。

当 abort 发生在计数增加之后、下载完成之前，future 被丢弃，await 后的减计数语句不会执行。计数可能长期大于零，而[后台让路检查](../src-tauri/src/media.rs#L940-L949) 遇到这个状态直接退出，造成预取逐渐失效。

与此同时，[Range 下载](../src-tauri/src/net.rs#L1155-L1187) 通过独立 `tokio::spawn` 创建子任务。父任务被 abort 后，丢弃 JoinHandle 不等于取消子任务。旧目标仍可能下载，且因分片锁释放，新目标或同片前台请求可能另起一组下载。Tauri 协议处理也独立 spawn 下载，[协议入口](../src-tauri/src/lib.rs#L151-L158) 没有把浏览器取消传播到上游。HTTP 桥则在下载结束后才写 socket，[桥入口](../src-tauri/src/bridge_http.rs#L139-L147)。

建议：

1. 用 Drop/RAII guard 管理计数，正常结束、错误、取消均归还；预取计数和活动集合也采用同样的清理方式。
2. 用任务组及取消令牌管理全部 Range 子请求，取消时真正终止网络读取；不要仅丢掉父任务句柄。
3. singleflight 保存可共享的下载状态，前台命中正在执行的预取时提升优先级；仍有前台订阅者的任务不因预取退出而中止。
4. 以播放器会话标识发出停止/换源信号。不要只依赖浏览器 XHR abort，特别是自定义协议路径。

验收：连续跨片拖动和连切 10 次后，前台计数最终归零；过期后台任务在受控测试中 200ms 内退出；同一规范化分片只有一个下载所有者。

### P0：全局预取代际与活跃时间混用，预热可能打断当前播放

**源码确认。** [全局状态](../src-tauri/src/media.rs#L226-L262)、[前台活跃窗口](../src-tauri/src/media.rs#L767-L789)、[普通预取换代](../src-tauri/src/media.rs#L820-L827)、[首片预热换代](../src-tauri/src/media.rs#L879-L889) 由所有视频共用。

问题包括：

- 每次普通分片请求、相邻集清单预热都可能递增同一个 generation，使当前视频任务与相邻集任务互相失效。
- 任一播放器请求会刷新全局 30 秒时间窗，不能代表某一旧视频仍被观看。
- 让路只在任务开始前检查；后台开始后，前台到来并不会抢占它。
- 首片 warmup 不经过普通预取的 3 任务限额，多个预热目标可能各自发出 8 路 Range 请求。
- [Feed 的相邻集预热](../src/components/Feed.tsx#L362-L394) 在 300ms 后启动，但没有检查 `active`、是否已经出首帧、当前缓冲是否充足；隐藏页面仍可能取地址、预热分片。

建议：

- 会话状态按 player/session + playlist + epoch 隔离；epoch 仅在换源、远跳、失活等语义变化时更新，不在每次正常顺序取片时更新。
- 统一下载调度，优先级为：已提交 seek 目标与当前缺片 > 当前续播补片 > 下一集/下一视频首片 > 回看/远端推测。
- 全局限制实际 HTTP 请求数与后台带宽，不只统计“分片任务数”。初期保留现有前台 8 路上限作为对照，不增加上限；后台同时最多一个重媒体预热目标。
- 下一集首片仅在当前播放已稳定、前向缓冲达到初始候选 8–12 秒后预热；阈值随后按码率、倍速、实测耗时调整。

### P1：移动端两种拖动没有使用已有推测预取

**源码确认。** 桌面进度条已在预览阶段调用 [prefetchAt](../src/components/Feed.tsx#L1191-L1196)，独立播放器也已接入。但主 Feed 的[横向手势预览](../src/components/Feed.tsx#L550-L556) 和[移动进度条预览](../src/components/Feed.tsx#L766-L784) 只更新界面状态，松手后才 seek。

建议复用 [createSeekPrefetch](../src/seekPrefetch.ts) 的分片去重，在两种预览入口传目标时间。补齐取消语义：取消拖动、失活、换源不仅清理前端 timer，也应取消后端推测任务；松手则把最终目标交接给前台，不取消仍需下载的同一片。先修 P0，再扩大推测预取覆盖，避免更多入口触发取消泄漏。

### P1：切集预热存在，但“切到另一部视频”主要仍是冷启动

**源码确认。** [邻接数据加载](../src/components/Feed.tsx#L292-L302) 只加载详情；[播放地址加载](../src/components/Feed.tsx#L325-L360) 只针对当前条目；[现有预热](../src/components/Feed.tsx#L362-L394) 主要针对同视频上一/下一集。

建议：

1. 当前缓冲健康后，按滑动方向优先解析下一部视频的播放地址，并预热清单、选中流的首片和首片所需 Key。只预热一个最可能目标，避免前后全拉。
2. 同视频顺序连播优先下一集；上一集已缓存时不重复预热。
3. 播放地址使用 TTL、账号/线路上下文与 in-flight Promise 去重。当前纯字符串 Map 没有过期时间；预热请求和前台请求也没有共享 Promise，快速切集可能重复请求。
4. 高清 HEVC 开启时，现有预热仍只调用 `mediaWarmup(main)`，目标播放却可能选 HEVC；应按实际选中流预热，不同时下载两套大分片。[选流](../src/components/Feed.tsx#L131-L134)、[预热流选择](../src/components/Feed.tsx#L377-L387)。
5. warmup 返回值应区分“清单拿到”“首片可用”“失败/取消”。目前 [warmup_playlist](../src-tauri/src/media.rs#L758-L765) 完成只意味着清单已加载、任务已排队，不代表切过去即可出画。

### P1：Range 路径有额外探测、重下和完整性校验缺口

**源码确认。** [实际下载实现](../src-tauri/src/net.rs#L1113-L1213) 与注释有差异：

- 先发 `bytes=0-0` 获取总长，之后再发 8 个 Range 请求，是至少 9 次请求，而非注释所述“第一块同时作为正式数据”。
- 探测收到 200 时直接另发整包请求，没有复用这个完整响应；小于 1MiB 的对象也多一次探测。
- 任一子请求失败后，仍按序等待所有句柄，再整包重下；故障恢复可能叠加大段等待。
- 子响应只检查 206，没有核对 Content-Range 区间、总长与精确预期字节数；短响应可能留下零填充且被当作成功缓存，随后表现为解码错误/反复恢复。
- HLS 分片超时配置 15 秒，而底层单次请求为 20 秒并可能叠加整包重试。前端结束等待不代表后端已经结束下载。[HLS 配置](../src/components/VideoSurface.tsx#L145-L151)、[底层整包请求](../src-tauri/src/net.rs#L1018-L1079)。

建议：复用有效探测数据，已知 Key/小对象直接整包；逐块验证区间与长度；失败尽早取消剩余任务，按总预算决定补失败块或整包回退。为源站不支持 Range、403、429 设置明确分类及退避，不盲目加并发。记录包括探测、排队、每块、回退在内的总耗时。

## 次级优化

### 按缓冲状态执行 seek，避免每次重启加载器

[VideoSurface](../src/components/VideoSurface.tsx#L80-L91) 与 [Player](../src/components/Player.tsx#L53-L64) 每次 seek 都先调用 `startLoad(target)`。本项目安装的 hls.js 1.6.19 在 [startLoad](../node_modules/hls.js/src/controller/stream-controller.ts#L138-L145) 内调用 stopLoad；[stopLoad](../node_modules/hls.js/src/controller/base-stream-controller.ts#L170-L185) 会 abort 当前片/Key 并重置 transmuxer。

已在 video.buffered 的目标可优先仅写 currentTime；加载已停止、MMS buffering 停止或故障恢复时才显式恢复加载。未缓冲目标应验证是否让 hls.js 原生 seeking 处理即可，避免以“优化”为名移除 MMS/失活恢复所需路径。保留现有 stall/lifecycle/mms 全部回归。

### 让缓存命中覆盖后台路径，降低磁盘与内存开销

[前台](../src-tauri/src/media.rs#L686-L700) 读取磁盘缓存，但[普通预取](../src-tauri/src/media.rs#L940-L975) 与[首片排队](../src-tauri/src/media.rs#L894-L923) 只检查内存；内存已淘汰但磁盘还在时，后台可能重新走网络。应共享统一的“内存 → 磁盘 → 网络”查找路径，并将磁盘 I/O 放入有界阻塞任务池。

[每次写盘](../src-tauri/src/media.rs#L158-L176) 新建线程并扫描目录淘汰；磁盘命中后调用 store_segment 又可能重写磁盘。建议单写入队列、已落盘命中不重写、批量/低频淘汰。内存按总字节预算而不只按 80 个分片限制。当前达到 500MiB 后一次清到 250MiB，回看命中率可能突降，可改成高低水位接近的滞回淘汰，具体阈值按设备设置。

### 减少列表重渲染和不必要的视觉等待

[Feed](../src/components/Feed.tsx#L140-L148) 每次 timeupdate 更新整个组件，并对 [全部 videoIds](../src/components/Feed.tsx#L858-L865) 建立 UI。长列表可保留高度占位，只渲染当前与邻接项；进度控件和静态元信息拆分，避免每个时间 tick 更新整页。

`buffered` 目前只初始化/重置，没有读取 video.buffered 更新，缓冲条不能代表真实缓冲。应展示实际 TimeRanges，而非仅一个从零开始的比例；分清 MSE 已缓冲区与后端已缓存区。首帧前保留封面/上一帧，下一帧就绪后再切换，替代纯黑等待；`onPlay` 不等同首帧，实际就绪使用 playing/requestVideoFrameCallback。不要为了隐藏黑屏启动多套长期解码器。

### HTTP 桥与构建入口一致性

[桥实现](../src-tauri/src/bridge_http.rs#L64-L83) 每连接一线程且 Connection: close，可后续改为有界异步 HTTP 服务、keep-alive 和断连取消。但本地 TCP 建连通常不是数秒卡顿的第一原因；Windows 桌面还走自定义协议，单改桥不会同时解决桌面下载浪费。大规模桥重构排在调度和取消修复之后。

## 如何验证优化确实有效

建议增加受控 Rust 代理测试服务器，返回正常/截断 Range、忽略 Range、慢块、403、429 及可观测取消，再将真实 Rust 代理接入浏览器回归。现有 fixture 不覆盖这些行为。

| 操作 | 建议验收目标（不是本轮已达到的真实网络指标） |
| --- | --- |
| 已缓冲/已缓存 seek | 恢复帧 P95 < 1 秒，单独记录 MSE 命中、内存命中和磁盘命中 |
| 未缓存 seek | 分开记录拖动开始、松手和恢复帧；报告冷/热缓存、下载字节和吞吐，不混入缓存样本 |
| 已完成预热的切集/切视频 | 用户确认切换至首帧 P95 < 1 秒 |
| 连切、取消拖动、页面失活 | 过期后台任务受控环境下 200ms 内退出，计数归零，不新增隐藏页预热 |
| 顺播与 2 倍速 | 测试窗口内卡顿次数/时长下降，前台缺片率下降，不靠多倍流量换结果 |
| 下载正确性 | 截断块不入缓存、Range 区间完全验证、相同分片只一个下载所有者 |
| CPU/内存 | 同一设备同一媒体比较，不持续双解码，不全片转码，不新增高频目录扫描 |

每次播放会话记录 `switch/seek request → queue → API → playlist → key/segment → append → rendered frame`，补充 session、epoch、priority、cache source、queue_ms、lock_wait_ms、TTFB、body_ms、cancel_reason、buffer_ahead_s、丢帧数。以首帧回调而非 API 成功或 play 事件结束计时。

若实际可用吞吐只有 5Mbps，一片 2.1–2.9MB 仅传输时间就约 3.4–4.6 秒，尚未包括 API、清单和解码。短时拖动预取能提前支付部分时间，但不等于任何冷远跳都可在 1 秒恢复。稳定亚秒应优先通过命中缓存、提前预热、较低码率实现；不引入实时转码来增加 CPU 负担。

[历史调优记录](playback-tuning.md#L5-L24) 中的 CDN 时延和 HTTP 协议支持仅作历史参考；特别是把单连接吞吐原因直接归于 hyper/RTT 的结论，本轮没有用包级证据重证，应保持为待验证解释，而非据此排除所有其他网络因素。

## 推荐实施顺序

1. **第一批：** RAII 计数、可传播取消、singleflight 交接与 Range 完整性校验。
2. **第二批：** 会话隔离调度、前台优先级、后台限额和 active/缓冲门槛。
3. **第三批：** 移动端推测预取、跨视频首片预热、选中流预热和播放地址去重/TTL。
4. **第四批：** 缓存后台命中、磁盘写入队列、按缓冲状态 seek、长列表 UI 降载。
5. 恢复正常上游连通后，以相同媒体和入口进行少量冷/热缓存 A/B 对比；不清空用户缓存，不反复下载同一真实 CDN 分片作压测。
