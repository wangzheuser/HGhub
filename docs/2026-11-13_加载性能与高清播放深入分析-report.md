# HGhub 加载性能与高清播放深入分析

**结论：仍有明显优化空间。优先修复预热就绪与会话交接，再优化冷分片传输；高清应按真实分辨率、可持续码率和解码平滑度选择，而非按 HEVC 标签判断。**

本轮仅分析。未修改应用源码、构建、重启或切换当前播放；新增本报告及忽略目录中的分析脚本/证据。只请求少量播放地址和清单，不额外从上游下载视频分片；画质检查复用现成磁盘缓存，在内存解密后由单线程 ffprobe 检查，未保存解密视频或输出密钥/签名 URL。

## 1. 证据与当前瓶颈

### 1.1 真实首片主要时间花在下载，不在解码

复核上一轮同一进程/验证 epoch，限定 `pid=280884`、2026-11-12T16:51:45Z 之后，未将日志前段其他进程的预热事件混入。

| 阶段 | 切到下一集 | 切到下一视频 |
| --- | ---: | ---: |
| 播放地址 | 切换前已做预解析，耗时约 1.098 秒 | 0.972 秒 |
| 清单 | 1.343 秒，仍为冷请求 | 0.576 秒 |
| AES key | 1.047 秒，与分片并行 | 1.355 秒，与分片并行 |
| 首片 | 2,243,792 字节，约 6.166 秒 | 3,964,736 字节，约 10.682 秒 |
| 客户端首字节 | 约 6.186 秒 | 10.726 秒 |
| 客户端片完整加载 | 约 6.188 秒 | 10.734 秒 |
| 加载结束到 playing | 约 0.179 秒 | 约 0.178 秒 |
| 整个操作至继续出画 | 8.238 秒 | 13.133 秒 |

出处：[切集时间线](../test-results/live-playback/2026-11-12T16-51-45-891Z/playback.log#L2667-L2740)、[跨视频时间线](../test-results/live-playback/2026-11-12T16-51-45-891Z/playback.log#L2795-L2867)、[计算结果](../test-results/loading-analysis-20261113-0917/history-analysis.json)。不同阶段存在并行、调度与不同起止点，表内数字不应机械相加。

当前关键路径近似为：

```text
首页取到视频 ID（仅首次首页需要）
  → 播放地址
  → 活动会话确认
  → 清单/子清单
  → max(首片下载, key/初始化依赖)
  → 解密、转封装与解码出画
```

确定事实：Feed 的 detail 与 play 已是并行 effect，不存在先等详情才请求播放地址的问题。当前 60 秒缓冲配置也不意味着起播要先攒满 60 秒。不要针对这两个误判再做重构。

### 1.2 当前交付方式放大了大分片起播等待

后端先完成首个 64KiB Range 探测，再对大对象展开最多 8 路 Range，全部组装成 Vec，之后才向播放器交付整个分片。上述跨视频样本的客户端首字节与完整片完成只差约 8ms，是全片缓冲屏障的运行证据。首探到后续 Range 派发间隔约 1.75–2.14 秒，该间隔包含首探请求及读完，不应全部称作 DNS 或可直接消除的 RTT。

出处：[Range 实现](../src-tauri/src/net.rs#L1218-L1323)、[媒体响应](../src-tauri/src/media.rs#L1438-L1444)。

此外，普通后台预取实际上也走 Range：`spawn_background(..., false)` 中的 false 只影响 key 预热，任务内部始终调用 `background_bytes(..., true)`。所以“最多一个后台任务”不等于“最多一个后台 HTTP 请求”。大对象通常是首探加 8 个区间请求，源码关于普通预取不展开 Range 的注释已与实现不符。

### 1.3 高清持续流畅首先受真实吞吐约束

历史跨视频首片包含 8.533 秒内容：

- 片级媒体码率约 **3.717Mbps**。
- 按客户端完整交付计算，有效速度约 **2.955Mbps**。
- 下载耗时/内容时长约 **1.258**，即该次交付比该片播放消耗更慢。
- 若坚持完整片到齐再出画，仅这片 1 秒传完就需要约 **31.718Mbps** 的有效载荷速度，尚未计入请求等待。

这些是单片样本，不代表整部剧平均码率或用户接入带宽上限，但足以说明：持续交付低于媒体消耗时，单纯增大缓存只能推迟下一次卡顿。客户端还需减少请求/调度损耗，或选择上游已有的更高压缩效率、可持续码率的同分辨率流。

### 1.4 “标准流”并不等于标清

本轮复用当前视频 1658 第 11 集缓存，实际测得：

| 属性 | 结果 |
| --- | --- |
| API 流名 | main，未提供 HEVC 备选 |
| 视频 | H.264 High，720 × 1280，30fps，yuv420p |
| 音频 | AAC-LC，44.1kHz，双声道 |
| 前 8 个缓存片的封装码率 | 约 3.506–3.561Mbps |
| 分片时长 | 约 3.633–5.2 秒，均值 4.969 秒 |
| 清单 | 单媒体清单，AES-128，无 EXT-X-PART，无 init-map |

[本轮实际缓存探测](../test-results/loading-analysis-20261113-0917/manifest-probe-1658-11.json)。这不是全站画质结论，但已提供反例：main 本身就可以是竖屏 720p 高清。当前 UI 将 HEVC 与“高清”、main 与“标准”绑定，容易误导画质判断。

另一个本轮清单样本 3273 第 1 集的平均片长为 **8.393 秒**、最大 8.533 秒，同样是 AES-128、无多码率 master/LL-HLS parts：[清单探测](../test-results/loading-analysis-20261113-0917/manifest-probe.json)。对这两个单层样本，开启 ABR 或 lowLatencyMode 不会凭空生成更短的片或新清晰度档位。

## 2. 第一优先级：把预热变成真正可交接的就绪资源

这是对切集、下一视频最值得先实施的低至中等规模改动，不扩大缓存和下载并发。

### 2.1 拆分地址预解析与媒体预热，避免门槛波动使工作白做

[现有 effect](../src/components/Feed.tsx#L374-L417) 只有连续缓冲达到 8 秒且不 waiting 才开始：先请求下一目标地址，再调用媒体预热。缓冲跌破 8 秒会清理整个 effect，将 alive 置为 false。

历史样本中，触发附近缓冲仅剩 **8.825 秒**，地址 API 却需 **1.098 秒**；在正常播放推进下，API 返回前就可能跌破门槛。该 epoch 没有 warmup.ok/fail，切集首片仍冷。**代码上的自取消条件确定存在；该次唯一取消原因仍属高概率推断，因为缺少 warm.skip/cancel 事件。**

建议拆成：

1. **轻预解析阶段**：当前源确定/首帧后，单候选解析下一目标地址及必要清单；不受 8 秒上下波动清理。复用现有 Promise/TTL，不新增多组请求。
2. **重媒体阶段**：缓冲健康且有预算才预取正确首片和依赖。使用进入/退出不同阈值，例如进入 8 秒、退出 4 秒只是初始实验值，并按倍速、实测片下载耗时折算为墙钟余量。
3. 仅切源、候选、画质、失活、明确 seek 改变任务代际；普通 timeupdate 不作废已经成功的地址解析。

### 2.2 切换时提升新目标任务，而不是全量取消再重新下载

[set_session](../src-tauri/src/media.rs#L383-L409) 在会话改变时取消全部后台任务。即将播放的新集首片若已下载一半，也会被撤销；现有 load_segment 的“保留同片”交接逻辑发生在另一条路径，越不过此前的全量取消。

应保留并提升与新目标 root/variant/首片匹配的在途任务，只取消不再需要的旧目标；按资源订阅者和明确代际管理取消。重任务仍保持有界，前台缺片/key 优先，不以保留预热为由让旧视频继续占带宽。

### 2.3 区分 queued、ready、cancelled，别把 accepted 当完成

[spawn_background](../src-tauri/src/media.rs#L1121-L1179) 返回 true 可代表已有缓存、已有任务或刚排队；[Feed](../src/components/Feed.tsx#L407-L410) 却据此记录 30 秒。后台随后被当前前台片抢占时，这个记录仍存在。

应提供至少：清单 ready、目标 variant、首片 ready、对应 key/init/audio ready、取消原因。只有所需资源真正就绪才标记 ready；首片缓存命中也要单独确认 key 等依赖。ready/queued/取消的日志必须带目标代际，便于验证命中率。

### 2.4 候选跟随用户意图，跨视频不应永远排在下一集后面

[当前候选](../src/components/Feed.tsx#L375-L379) 只要有下一集就选下一集，下一视频很难得到预热。应按滚动方向、切集操作、选集面板按下/焦点及当前交互模式选择候选；仍只保留一个重媒体目标，不同时拉下一集和下一部。

## 3. 第二优先级：缩短真正的冷加载链路

### 3.1 Range 自适应，而不是继续硬加到 12/16 路

保留单 GET、2/4/8 档，根据同主机实际 TTFB、对象大小、总完成时间和错误率选择。小 key/清单不需要先探 64KiB 再分段。探测到并校验 Content-Range 后，可评估首块读取与余块派发重叠，保持最终完整校验；不要增加额外 HEAD 前探。

目前证据足以定位首探屏障，但尚不足认定单 GET 必胜 8 路。先补被动阶段统计：首探 headers/body、真实 HTTP 数、最慢子块、回退原因、最终字节、缓存来源，再做少量串行、等价条件的探索比较。已有记录显示简单加并发或强制 HTTP/2 并非稳定收益方向。

### 3.2 补小对象 singleflight，并统一清单原文缓存

[load_segment](../src-tauri/src/media.rs#L851-L927) 锁前查 KEY_CACHE，锁后仅查 SEG_CACHE；key 等待者可能再次下载已完成的小对象。应在锁后复查两者或共享同一完成结果。

预热 load_playlist 走 PL_CACHE，master 子清单经 /seg 走 KEY_CACHE，原始获取有分流。建议按原始清单身份共享获取/去重，再按本地 prefix 派生改写结果，保留动态清单 TTL 与 URL/签名语义，避免预热后播放器再拉一次。

单独预热 key 不会省下表内所有 key 耗时：历史样本 key 已与更慢的首片并行，优化目标是消除重复请求与偶发关键路径，而非机械相加。

### 3.3 首帧前减少无关业务竞争

保留 detail 与 play 的并行。related 延至首帧或打开面板，非 active Feed 不再新增业务请求，detail 使用有界在途去重和短 TTL。当前跨视频 detail/related/play 同时发出；收益幅度尚待比较，首片十秒仍是主矛盾。

### 3.4 渐进交付值得做原型，但不是改一个 HLS 参数

真正的大方向是：分片仍在下载时，将连续、可消费的数据推进解密/转封装和播放，而非等完整片 Vec。需同时满足：

- 后端响应能流式交付，缓存只提交完整校验成功的对象。
- Tauri 当前自定义协议 Response<Vec> 的限制得到解决，或选定可靠的传输适配。
- hls.js 使用支持 progressive 的 loader，TS 转封装与 AES 路径可渐进。
- AES-CBC 块对齐、IV、尾部 padding、失败/取消、同片交接处理正确。

本地 hls.js 1.6.19 的 [streaming 配置](../node_modules/hls.js/src/config.ts#L731-L748) 与 [软件渐进 AES 路径](../node_modules/hls.js/src/demux/transmuxer.ts#L120-L165) 提供可行性线索，但软件 AES 可能增加客户端 CPU。优先在隔离开关下验证真实首帧、CPU 与掉帧，不以 HTTP 首字节更早替代实际出画收益。对原本没有 LL-HLS parts 的源，单开 lowLatencyMode 也不是替代方案。

## 4. 高清且流畅的策略

1. **显示真实质量**：分辨率如 720p/1080p 单独展示，AVC/HEVC 是编码标签；只在解析出真实值后显示，不将 main 当作标清。
2. **能力检查不止支持**：保留现有 MSE 检查，补缓存的 MediaCapabilities supported/smooth/powerEfficient，以及低频掉帧与真实尺寸采样；不把异步探测放在每次首播必等链路。
3. **优先同分辨率更高效率流**：上游提供且硬件平滑解码时评估 HEVC，否则选可持续的 AVC。该设备此前 HEVC MSE 为 false，不应强推；本轮样本本身也没有 HEVC 备选。
4. **按真实网络预算升档**：多码率源才应用 ABR。忽略或区分缓存回包测速，避免本地快速命中误导升档；预热/seek 与实际 rendition 一致。最新单层样本没有切档空间。
5. **缓冲按倍速折算**：约 3.5Mbps 的样本在 1 倍速可先以约 1.3–1.5 倍实测码率作为余量试验，2 倍速还需相应翻倍。余量来自实际 CDN 交付，不是宽带套餐速率。
6. **换画质/回退保留进度**：保存 currentTime、播放意图与 rate，新源准备后恢复。当前换源会重建 HLS，缺少通用的同位置质量切换恢复；且任意 HEVC 错误都会标成解码失败，网络错误与 codec 错误应分开。
7. **减少无效恢复**：非致命错误先交给 hls.js 内建恢复，不额外反复 startLoad；统一前后端阶段预算与总恢复预算，避免前端 15 秒超时与后端最多 20+20 秒错位。不要简单缩短超时误伤真实大片。

持续吞吐低于媒体码率时，快起播、最高档和无限时无停顿存在物理取舍。优先消除客户端浪费，并在上游实际提供的质量档位中选择；放大显示尺寸并不生成更高清源。

| 桥响应重复 Content-Length | 本轮两个清单原始 HTTP 响应均出现 2 个；Node fetch 首次失败。media.respond 已写，bridge.write_media 再写并透传一次 | 只保留一个正确长度；完善严格 HTTP 客户端回归。桌面自定义协议不经过该桥，不归因为桌面 13 秒 |

## 6. 建议实施顺序和验收

| 顺序 | 实施包 | 核心验收 |
| --- | --- | --- |
| 1 | 两阶段预热、迟滞、正确候选、queued/ready 状态和匹配目标交接 | 预热不因普通时间推进丢失；同资源在途提升不重下；错误候选立即取消 |
| 2 | key/清单去重、延后无关请求、统一有界恢复 | 同目标无重复 key/清单；慢片无多层恢复风暴；错误退出后明确可重试 |
| 3 | 被动 Range 阶段计时与小规模自适应探索 | 同条件冷片总耗时/失败率改善，而非只看回包速度；不增加 CPU/HTTP 峰值 |
| 4 | 真实画质与平滑度选择、切画质续播 | 实际分辨率与标签一致；网络/解码错误分开；中途换源保持位置、倍速和播放意图 |
| 5 | 渐进交付原型 | 同码率、缓存 miss 下真实首帧提前，CPU/掉帧可接受；中断片不入缓存 |

验收需要分开：真正首次冷首播、播放地址热/分片冷、首片/key/清单全部 ready 的热切换、随机未缓存 seek，以及稳定高清播放。已 ready 的切集/切视频以接近或低于 1 秒出画为目标；完全冷目标的成绩单列，不提前承诺亚秒。

统计至少包括：操作→首个实际渲染帧、地址/清单/首探/最慢子块/整片/解码阶段、字节与请求数、预热 ready/取消率、播放停顿占比、掉帧率、实际分辨率/码率/codec、CPU、缓存驻留与在途峰值。首轮仅少量串行样本验证方向，长期分位使用正常播放的被动统计，避免持续额外测速。

现有 64MiB 单片、192MiB 总缓存、单后台重任务、RAII、JoinSet 取消、严格 Range 校验和连接池保活继续保留。它们已解决正确性和缓存问题；下一轮重点是预热真正生效、冷片交付和真实高清策略，而不是重复扩大缓存或替换播放器引擎。
